# 产品设计：会话接力（Session Handoff）

> 一句话定位：**让「换个会话继续干」变得像按一次发送键那么轻。**
> 版本：v0.2 ｜ 关联：[技术设计](./03-技术设计.md) · [可行性](./04-可行性分析.md) · [调研](./02-同类插件调研.md)

---

## 1. 问题

DSH 的会话是「一次性上下文」：上下文满、换模型/预设、任务收尾、交接给同事时，用户面对的是同一件事——
**把已经发生的一切重新讲一遍**。现状的替代方案都不好：

| 现状 | 用户实际体验 |
|---|---|
| 开新会话，手写一段「之前做了…」 | 靠记忆复述，必漏；长任务要写十几分钟 |
| 继续在旧会话里写 | 上下文越来越贵，压缩后细节丢失 |
| `fork` 整个历史 | 成本没降，只是换了个会话 id |
| 用压缩（`/compact`） | 只能留在同一会话，摘要不可读、不可带走、不可交接 |
| 装迁移类插件（Bridge） | 面向「换预设」，入口在菜单/命令，流程是迁移而非日常动作 |

真正的痛点不是「没有摘要」，而是：**摘要在哪、能不能读、能不能改、下个会话能不能直接用。**

## 2. 目标用户与场景

| 用户 | 场景 | 成功标准 |
|---|---|---|
| 长任务开发者 | 一个需求做了 2 小时，上下文快满，想开个干净会话继续 | 新会话第一轮就能干活，不用重新解释 |
| 多模型/多预设用户 | 前半段用推理模型规划，后半段用快模型实现 | 新会话带上结论，切换不丢状态 |
| 协作者 | 把手里的一摊活交给同事或另一个 Agent | 一份可读的 Markdown，同事看完能接 |
| 留档型用户 | 一个阶段结束，想把「做了什么/为什么」留档 | 文档进 Git，可检索、可回顾 |
| 自动化用户 | 定时任务/子代理跑完，需要把结果带回主会话 | 结构化 JSON + 摘要，可被程序消费 |

## 3. 价值主张

1. **一次点击，不是一套流程**：按钮就在提交键旁，不需要记命令、不需要开菜单。
2. **产物优先**：先有一份人读的 `WorkSummary.md`，再有提示词；摘要不是黑盒内存。
3. **可审阅**：默认只预填草稿，发送前你能改；不想要就直接丢掉。
4. **干净的新会话**：只带结论与文件指针，不背历史包袱，成本可控。
5. **不牺牲旧会话**：原会话原样保留，随时可回去查。

## 4. 用户旅程

### 旅程 A：上下文快满了（主路径）

1. 用户看到上下文占用变高，点输入框右侧「接力」按钮；
2. 按钮转圈（5–30s），期间可继续看当前会话（不阻塞输入）；
3. 自动切到同工作区的新会话，输入框已填好交接提示词；
4. 用户扫一眼、改两句、按发送；
5. 新会话先读交接文档，再从「下一步」第一项开始。

**设计要点**：不弹窗、不要求逐段确认；确认发生在「发送前的那一眼」。

### 旅程 B：交接给同事

1. 点按钮 → 生成文档；
2. 在文件管理器/编辑器打开 `WorkSummary.md`，补两句背景；
3. 发给同事，或提交到仓库；
4. 同事按文档里的「下一步」接手。

**设计要点**：文档是普通 Markdown，路径稳定、可进 Git，不依赖 DSH 在线。

### 旅程 C：换模型/预设继续

1. 点按钮 → 新会话草稿；
2. 在新会话里切换模型/预设（DSH 原生控件）；
3. 发送。

**设计要点**：我们不替用户切模型；交接包与模型无关。

## 5. 交互规格

### 5.1 按钮

| 项 | 规格 |
|---|---|
| 位置 | 输入框右侧工具行，模型选择器左侧（`conversation.input.right`），即发送键所在行的紧凑控件位 |
| 形态 | 28×28 图标按钮，方框 + 出栈箭头 |
| 文案 | tooltip/aria：`接力到新会话` / `Summarize this session and continue in a new one` |
| 状态 | idle / busy（转圈，禁用）/ done（1.2s 绿色）/ error（1.2s 红色 + toast） |
| 键盘 | `Cmd/Ctrl+Shift+H`（macOS/Windows）；`Cmd/Ctrl+Shift+.`（Linux，DSH 保留 `primary+KeyH`） |
| 空态 | 无会话时不渲染（session 作用域本身保证有会话） |

### 5.2 反馈

- 成功 toast：`已生成交接文档，新会话已预填提示词：<标题>`
- autoSend 成功：`已生成交接文档并发送到新会话：<标题>`
- 失败 toast：`会话接力失败：<原因>`；原因尽量可行动（端点未注册 / 无工作目录 / 模型超时→已降级 / 创建会话失败）
- 不阻塞输入：整个流程不锁编辑器和发送键。

### 5.3 交接提示词（新会话的第一句话）

```markdown
# 会话接力：<标题>

上一会话（`session-…`）已完成一轮工作，下面是它的交接材料。

## 先读这两份文件
- 交接文档（必读）：`/abs/.../WorkSummary.md`
- 结构化数据：`/abs/.../handoff.json`

## 一句话状态
…
## 目标
…
## 已完成
…
## 下一步
1. … —— 为什么
## 参考文件
- `path`
## 交接要求
1. 先 Read 交接文档确认状态，不要凭摘要猜测细节；
2. 从下一步第一项开始；状态不一致先说明差异；
3. 优先在参考文件里找要改的文件；新发现补进文档；
4. 完成后说明目标/改动/验证。
```

设计意图：**把「读文档」变成新会话的第一步动作**，而不是让模型凭一段摘要直接开工。

### 5.4 预览编辑（v0.2 已实现）

生成后、打开新会话前弹出一张覆盖整页的模态卡片（`shell.overlay`，Esc 或点遮罩关闭）：

- 只读区：标题、一句话状态、下一步、记忆候选、交接文档路径（可复制）；
- 可编辑区：发往新会话的提示词（等宽字体，支持 Markdown）；
- 参考文件：勾选/取消后立即用结构化分段重建提示词；手动编辑提示词后勾选锁定，避免覆盖编辑；
- 动作：`打开新会话`（用编辑后的提示词）、`复制提示词`、`重新生成`、`关闭`（Esc/遮罩）；
- 交接文档不因编辑而改变：文档是稳定的评审产物，编辑只影响「新会话怎么被交代」；
- 想回到 v0.1 的一键直达：`preview: false`。

## 6. 交接包信息架构

| 层 | 内容 | 给谁看 |
|---|---|---|
| 提示词 | 一句话状态 + 下一步 + 文档路径 + 参考文件 | 新会话的模型 |
| `WorkSummary.md` | 五段式 + 记忆候选 + 参考文件 + 工具附录 | 人（同事/未来的自己） |
| `handoff.json` | 同数据的结构化版本 + 源会话元数据 | 程序（自动化/插件） |
| `交接记忆.md` | 跨会话仍然成立的事实，按时间分段 | 未来的会话/用户 |

**原则**：任何一层单独存在都要有价值；不要求读者同时读三层。

## 7. 记忆固化的产品规则

| 规则 | 说明 |
|---|---|
| 只收「跨会话仍然成立」的内容 | 偏好、约定、环境事实、可复用教训；不收本次进度 |
| 每条带 scope | `memory`（工作记忆）/ `user`（用户画像）/ `project`（项目约定） |
| 可见 | 文档里单独一节，台账是普通 Markdown |
| 可审 | 默认只落台账，不直接改每轮注入的运行时记忆 |
| 去重 | 台账已有同样文本就不重复追加 |
| 可撤销 | 用户删掉即不再出现（除非模型再次产出） |
| v0.2 晋升 | 显式动作：把候选「存入记忆」（对接 mnemon 等项目档案/记忆空间） |

**为什么这么保守**：记忆写错比摘要写错更贵——它会跟着用户很久。第一版先保证「写得可追溯、删得掉」。

## 8. 关键设计决策与取舍

| 决策 | 选择 | 取舍 |
|---|---|---|
| 入口 | 常驻按钮（提交键旁） | 比菜单/命令快，但占一个视觉位置；图标足够轻 |
| 确认方式 | 预览卡 + 预填草稿 | 编辑与确认合一；代价是多一次点击（可 `preview: false` 关掉） |
| 历史继承 | 不 fork | 新会话便宜、干净；代价是细节靠文档而非模型记忆 |
| 产物载体 | Markdown + JSON | 通用、可进 Git；代价是要管理文件目录 |
| 记忆 | 独立台账 | 安全、可删；代价是暂时不与记忆插件互通 |
| 模型 | 沿用会话路由 | 零配置；代价是会话中途换模型时路由取最后一次 |
| 失败 | 确定性兜底 | 永远有产出；代价是兜底质量一般（会标注） |

## 9. 隐私与信任

- 交接文档只写本地工作目录，**不上传**；
- 摘要只用用户已配置的模型路由，插件不新增网络请求；
- 文档可能包含代码片段与路径：默认 0600、目录在项目内，提醒用户**发出去前自行检查敏感信息**；
- 记忆候选可能含用户偏好：只落本地台账，不自动进入全局记忆。

## 10. 与同类产品的差异（产品视角）

- **vs dsh-plugin-bridge**：它是「换预设的搬家车」，流程完整但重；我们是「随手存档并续摊的便签」，入口更近、产物更像工作总结。
- **vs dsh-context-zip**：它解决「上下文被压掉后怎么回查」；我们解决「主动换会话时怎么交出去」。
- **vs dsh-auto-memory / mnemon**：它们让 Agent「记得」；我们让用户「交得出去」，并且把记忆候选交给人审。
- **vs fork / compaction**：那两者保留历史；我们卸载历史、保留结论。

## 11. 指标

**北极星**：新会话首轮「无需补充背景即可开始执行」的比例（人工抽检 + 用户自评）。
**过程指标**：

- 按钮点击 → 成功生成文档的比例（目标 > 95%，降级也算成功）；
- 生成后 24h 内新会话至少发送 1 轮的比例（衡量「预填草稿」是否被用）；
- 文档被再次打开/被 Read 的比例（衡量产物价值）；
- 平均交接耗时与摘要 token 成本。

**护栏**：

- 误发送率（autoSend 场景）≈ 0；
- 记忆台账「被用户删除的条目再次出现」的次数 ≈ 0；
- 插件导致会话页异常的次数 = 0。

## 13. 开放问题

1. **交接摘要要不要默认写进会话标题？**（方便在侧栏找到「上一次」）——暂不，避免改会话状态。
2. **新会话是否自动命名为「接力：<标题>」？** 官方 `startSession` 没有标题入参；可能要等 DSH 暴露或走 rename API。
3. **记忆台账放项目里还是放 `~/.dsh`？** 放项目里可随仓库共享，但可能被误提交；v0.2 提供 `.gitignore` 建议。
4. **多人协作时交接文档的冲突**：先按「时间戳目录 + 从不覆盖」处理，不做合并。
5. **是否需要在交接文档里保留完整工具输出？** 现在只保留摘要与最近 60 条时间线；完整日志仍在 DSH 会话里可查。
